1Research Background背景与问题

旧的评测问的是「你有没有走对那串步骤」

Old benchmarks asked whether the agent followed the right sequence of actions — not whether the task got done.

Prior Practice

比对动作序列

AITW、AndroidControl 等数据集把 Agent 的每一步动作与人类示范逐步比对。

Why It Breaks

在线环境不听话

真实环境里可以走多条不同路径，环境本身非确定，Agent 还会从错误中自我纠正。

Missing Signal

「像不像」≠「成没成」

论文主张：只有直接对最终状态给奖励，才是评测的金标准。

如果只看动作像不像标准答案，我们究竟在评测 Agent，还是在评测它像不像人类？

2Mechanism 1 / 3动态实例化

Dynamic 发生在参数层，不在任务结构层

Dynamic at the parameter level — not at the task-structure level.

变的是
标题 · 时间 · 地点 · 金额 · 分类 · 文件名 · 干扰项数量
not
不变的是
任务本体仍由 116 个模板决定，结构、意图、判分逻辑全部人工设计
  • 所以「百万级任务实例」不等于「百万种任务类型」——这是最容易被误读的一点
  • 代码里手工任务是 91 个，另 25 个由配置文件动态生成，合计 116
  • 准确表述应是「固定模板 + 随机参数实例化」，而不是「每次都面对未知的任务结构」
  • 论文自己也承认：参数化的难点在于判分逻辑必须在所有实例上依然成立

2Mechanism 2 / 3结果导向奖励

奖励读的是设备的真实状态，不是 Agent 的动作

Reward comes from the device's final state, not from the agent's action sequence.

① 构造起点
重置设备时间、还原应用快照，得到确定的初始状态
② Agent 自由操作
走哪条路径不管，多条路径皆可
③ 检查真实状态
文件系统 / 应用数据库 / 系统设置
④ 清理复原
teardown 还原现场，供下一个任务使用
原文 Table 2 ｜ 每个任务配一个校验逻辑：event_exists、message_exists、file_exists、timer.displays、wifi.enabled……查的都是真实状态，而不是屏幕。
  • 这种机制是非侵入式的：不需要修改应用源码，因此能把闭源应用也纳入评测（AndroidEnv 要求改源码，所以只能匹配自己写的应用）
  • 只有当系统状态确实不可查时，才退回看屏幕，例如秒表是否处于暂停

3Evaluation主结果

人类 80%，最好的 Agent 只有 30.6%

Ample headroom — but not a floor.

原文 Table 3 ｜ Success Rates (SR) on AndroidWorld and MobileMiniWoB++. 加粗为该列最优。
  • 区分度良好：既没碰到天花板，也没沉到地板——仍是一个能推动研究的区间
  • 人类 80% 是本实验协议下的结果，不代表人类能力上限
  • SeeAct 在安卓上只有 15.5%，说明把桌面网页 Agent 直接搬到安卓，迁移不是免费的
  • 实验设置：随机种子固定 30、温度固定 0；M3A 平均每任务约 3.9 分钟（纯文本版 2.5 分钟）

3EvaluationAgent 外壳的作用

同一个 GPT-4，换个 Agent 外壳，分数涨了一半

Performance depends on scaffolding, not only on the base model.

M3A-Simple · GPT-4 Turbo

19.8%

最小化提示词，没有操作指南，也没有反思机制。

M3A · GPT-4 Turbo

30.6%

加入 ReAct / Reflexion 式提示、安卓操作指南与界面表示规范化。

  • 提升不来自换模型，而来自提示词工程、领域知识与界面表示法
  • 反向证据：GPT-4 换成多模态 SoM 输入，在 AndroidWorld 上降到 25.4%，低于纯文本的 30.6%
  • 但同一个 SoM 变体在 MobileMiniWoB++ 上拿到 67.7%，是全表最高——结论随环境翻转
  • 论文解释：网页任务的无障碍树往往不完整，SoM 的视觉标注在那里才不可替代

3Evaluation鲁棒性分析

换个随机种子，任务难度就变了

Task parameterization fundamentally changes task difficulty.

原文 Figure 3 ｜ 圆点 = 固定种子，斜纹 = 不同种子。带 * 者为差异显著（p < 0.05）。
  • 固定种子下成功率常常近乎 0——论文称之为种子的「bad luck」
  • 跨三个种子，M3A 得分为 27.6% / 26.3% / 33.2%（均值 29.0%）
  • 统计上显著的只有 AddExpense 与 EditNote，不是全部任务
  • 换设备（Pixel 5 / Android 12）得 28.4%，波动幅度与换种子相当
  • 具体案例：ExpenseAddSingle 中种子决定要选的分类；若该分类不在首屏，Agent 因不会滚动而直接失败
  • 分寸要读准：设备对比只说明「保住了基本能力」，不等于实现了任意设备上的泛化

4Critical Assessment辩证评价

它在任何单项上都不是「最」的

Not the largest, not the first. The value is in the combination.

What It Is Not

不是什么

应用数 20、任务数 116，都不算大——AITW 有 3 万条数据。

也不是唯一采用 state-based 评测的 benchmark，OSWorld 已在做桌面版。

What It Is

是什么

第一个把下面五件事完整组合成公开、可复现框架的工作：

真实安卓环境 · 参数化实例 · 可执行 Agent · 最终状态评测 · 鲁棒性实验

  • 单看每一项都有人做过，难的是把它们拼成一个能跑起来、能复现的整体
  • 这才是它被 ICLR 接收的理由——工程整合本身也是一种学术贡献

4Critical Assessment局限性

可扩展性 ≠ 可移植性

The framework scales. Plugging in an arbitrary app does not.

可扩展 ✓
框架能在模拟器里运行，也能继续添加新任务
not
可移植 ✗
接入任意 APK 或真机，并不会自动得到一套可评测任务
Coupling

应用与初始状态

每个任务都绑定特定应用与特定的起点构造方式。

Coupling

参数生成与动作接口

随机参数的范围、UI 与动作的映射，都需逐应用适配。

Coupling

判分器

耦合最深的一环，必须知道该应用的数据库结构。

  • 这五者相互绑定，没有任何一个能自动迁移到新应用上
  • 论文对此是诚实的：它把可复现性做到了极致，代价是可移植性被冻结在已适配的 20 个应用里

4Critical Assessment历史定位

一个重要的中间阶段，不是最终答案

A significant step from static benchmarks toward open-world agent evaluation — not the destination.

Avoid Saying

不建议这样说

「它解决了 Android Agent 的泛化问题」

任务结构和应用范围仍由人工设计，动态只是参数级的。

Better Framing

建议这样说

「它推动了 Agent Benchmark 从静态轨迹、固定任务，走向真实环境、动态实例化、结果导向评测。」

它的贡献不是更强的 Agent，而是更接近真实世界的评测方式。 任务结构与应用范围仍由人工设计，因此它更适合作为走向开放世界评测的中间阶段
